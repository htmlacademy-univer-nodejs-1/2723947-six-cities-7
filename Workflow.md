# Как работать над проектом

## Окружение

Для удобства работы над проектом используются инструменты из **Node.js** и **npm**. Все необходимые настройки произведены. Убедитесь, что на рабочем компьютере установлен актуальный LTS релиз Node.js**. Актуальная версия **Node.js** указана в файле `package.json` в поле `node`. Затем, в терминале, перейдите в директорию с проектом и _единожды_ запустите команду:

```bash
npm install
```

Команда запустит процесс установки зависимостей проекта из **npm**.

### Сценарии

В `package.json` предопределено несколько сценариев.

#### Скомпилировать проект

```bash
npm run compile
```

Создаст директорию `dist` и скомпилирует проект.

#### Удалить скомпилированный проект

```bash
npm run clean
```

Удаляет директорию `dist`. Используется перед компиляцией.

#### Собрать проект

```bash
npm run build
```

Выполняет сборку проекта: удаляет ранее скомпилированный проект и компилирует заново.

#### Проверить линтером

```bash
npm run lint
```

Запуск проверки проекта статическим анализатором кода **ESLint**.

Линтер проверяет файлы только внутри директории `src`.

**Обратите внимание**, при запуске данной команды, ошибки выводятся в терминал.

#### Запустить ts-модуль без компиляции

```bash
npm run ts -- <Путь к модулю с ts-кодом>
```

Пакет `ts-node` позволяет выполнить TS-код в Node.js без предварительной компиляции. Используется только на этапе разработки.

#### Запустить проект

```bash
npm start
```

В процессе запуска проекта будет выполнен процесс «Сборки проекта» и запуска результирующего кода.

#### Запустить CLI

```bash
npm run cli -- --help
npm run cli -- --version
npm run cli -- --import ./mocks/offers.tsv 'mongodb://admin:test@127.0.0.1:27017/six-cities?authSource=admin'
npm run cli -- --generate 100 ./generated-offers.tsv http://localhost:3000/offers
```

Без параметров CLI показывает справку. Команда `--import <path> <mongodb-uri>` читает TSV потоково и сохраняет предложения в MongoDB. URI включает имя базы и параметры аутентификации; при специальных символах в логине или пароле используйте URL-кодирование. Первая строка может содержать названия столбцов. Поля разделяются табуляцией; фотографии и удобства внутри поля разделяются точкой с запятой. Порядок столбцов приведён в `mocks/offers.tsv`.

`authorEmail` определяет автора. Импорт ищет пользователя по email, а если его нет — создаёт пользователя типа `regular`, с именем из первых 15 символов части email перед `@`, аватаром `default-avatar.png` и случайным паролем из 12 символов. В коллекции `users` хранится только хеш пароля scrypt с индивидуальной случайной солью. Пароль не выводится; эти пользователи предназначены для тестовых данных. Email защищён уникальным индексом. В коллекции `offers` автор хранится как ObjectId со ссылкой на `users`, количество комментариев изначально равно нулю. Обе коллекции имеют `createdAt` и `updatedAt`. Повторный импорт использует существующих авторов, но создаёт новые предложения.

Команда `--generate <n> <filepath> <url>` получает заготовки по указанному URL и потоково записывает `n` случайных предложений в новый TSV-файл с заголовком. `n` — положительное целое число. Существующий файл не перезаписывается. Фотографии, город и координаты берутся из одной заготовки; дата, рейтинг, стоимость, тип жилья, вместимость и удобства выбираются случайно. Избранное изначально выключено. Комментарии не генерируются.

Обе команды учитывают скорость записи: даже файлы больше 2 ГБ обрабатываются без загрузки целиком в память. Импорт последовательно ожидает запись каждого предложения и выводит итоговое количество, без JSON документов. В логах отражаются попытка подключения, установленное соединение и его закрытие; URI и учётные данные не выводятся. При ошибке MongoDB, чтения или формата импорт останавливается с ненулевым кодом и количеством уже сохранённых предложений. Ранее записанные документы остаются в базе: весь файл не оборачивается в транзакцию. Соединение закрывается и при успехе, и при ошибке. Для защиты от повреждённых файлов длина одной строки ограничена 64 КиБ. Сгенерированные `*.tsv` исключены из Git; `mocks/offers.tsv` остаётся учебным примером.

#### Проверить приложение и CLI автоматическими тестами

```bash
npm test
```

Собирает проект и проверяет загрузку и валидацию конфигурации приложения, безопасный вывод логов, генерацию, импорт, ошибки и сохранение существующих файлов. Тесты самостоятельно запускают временный HTTP-сервер на свободном локальном порту.

Для проверки сервисов и CLI с настоящей MongoDB запустите Docker Compose и выполните:

```bash
MONGODB_TEST_URI='mongodb://admin:test@127.0.0.1:27017/six-cities?authSource=admin' npm test
```

Интеграционный тест создаёт отдельную базу со случайным именем `six_cities_test_*` и удаляет её после проверки. Проверяются поиск и создание документов, уникальность email, хеш пароля, ссылки на автора, служебные даты, повторный импорт и закрытие соединения при ошибках TSV и чтения файла. Без `MONGODB_TEST_URI` этот тест пропускается. Переменная нужна только тестам; приложение её не использует.

#### Запустить тестовый REST API

```bash
npm run mock:server
```

Запускает JSON-server с шестью заготовками из `mocks/mock-server-data.json`. Ресурс для генератора: `http://localhost:3000/offers`. Чтобы изменить порт, выполните `npm run mock:server -- --port 3001` и передайте генератору соответствующий URL.

## Запуск проекта

1. Установите Node.js версии 18 или новее и зависимости командой `npm install`.
2. Для запуска приложения скопируйте `.env.example` в `.env`, задайте собственную случайную соль и выполните `npm start` (JSON-логи) или `npm run start:pretty` (читаемые логи; требуется Bash). Приложение проверит конфигурацию, выведет порт и сообщение об инициализации. HTTP-сервер на этом этапе ещё не запускается.
3. Запустите MongoDB и mongo-express командой `docker compose up -d` (см. ниже). Для генерации TSV в отдельном терминале запустите `npm run mock:server`.
4. Во втором терминале выполните `npm run cli -- --generate 100 ./generated-offers.tsv http://localhost:3000/offers`.
5. Импортируйте данные: `npm run cli -- --import ./generated-offers.tsv 'mongodb://admin:test@127.0.0.1:27017/six-cities?authSource=admin'`.

CLI получает URI MongoDB, адрес JSON-сервера и путь к файлу аргументами; `.env` и переменные окружения приложения для него не требуются. Модуль запуска приложения пока проверяет конфигурацию и пишет логи; соединение с базой на данном этапе используется командой импорта.

### Запуск MongoDB в Docker

Установите и запустите Docker Desktop с поддержкой Docker Compose. Из корня проекта выполните:

```bash
docker compose up -d
docker compose ps
```

Файл `docker-compose.yml` запускает актуальный официальный образ `mongo:latest` (вместо устаревшей 4.2 из примера задания) и mongo-express 1.0.2. Поле `version` не требуется современному Docker Compose. Интерфейс mongo-express запускается после успешной проверки готовности базы. Для обновления образов выполните `docker compose pull`, затем `docker compose up -d`.

MongoDB доступна по адресу `mongodb://admin:test@127.0.0.1:27017/?authSource=admin`. Веб-интерфейс: `http://localhost:8081`, логин `admin`, пароль `test`. Оба порта доступны только с локального компьютера. Учётные данные в Compose предназначены для локальной разработки.

Проверить подключение с аутентификацией:

```bash
docker compose exec db mongosh --username admin --password test --authenticationDatabase admin --quiet --eval 'db.adminCommand({ping: 1})'
```

Ответ должен содержать `ok: 1`. Посмотреть логи можно командой `docker compose logs --tail=50 db db_ui`. Остановить и удалить контейнеры — `docker compose down`. Данные сохраняются в именованном томе `six-cities_data` и доступны при следующем запуске. Команда `docker compose down -v` удаляет также том и все данные базы.

`MONGO_INITDB_ROOT_USERNAME=admin` и `MONGO_INITDB_ROOT_PASSWORD=test` задают пользователя при первом запуске с пустым томом. При смене этих значений обновите также параметры `ME_CONFIG_MONGODB_ADMINUSERNAME`, `ME_CONFIG_MONGODB_ADMINPASSWORD` и `ME_CONFIG_MONGODB_URL`. Изменение переменных не меняет пароль пользователя в уже созданной базе. `ME_CONFIG_BASICAUTH_USERNAME=admin` и `ME_CONFIG_BASICAUTH_PASSWORD=test` задают отдельный вход в веб-интерфейс.

### Проверка большого файла

После сборки (`npm run build`) можно запускать CLI напрямую, чтобы не пересобирать его перед каждой командой:

```bash
node dist/cli.js --generate 5000000 ./large-offers.tsv http://localhost:3000/offers
node dist/cli.js --import ./large-offers.tsv 'mongodb://admin:test@127.0.0.1:27017/six-cities?authSource=admin'
```

Получится файл больше 2 ГБ. Импорт такого файла последовательно записывает миллионы документов в MongoDB и может занять много времени и места на диске. В терминал выводятся только служебные логи и итоговый счётчик. Для экспериментов используйте отдельную базу, указав её имя в URI. После проверки большой TSV-файл можно удалить. Эти данные не нужно коммитить.

## Структура проекта

### Директория `src`

Исходный код проекта: компоненты, модули и так далее. Новые модули организуются по назначению: `src/app` — приложение, `src/shared/logger` — логирование, `src/shared/config` — конфигурация, `src/shared/di` — контейнер и идентификаторы зависимостей. Контракты хранятся в `*.interface.ts`, реализации — в отдельных модулях с именами в kebab-case. Модули предметной области в дальнейшем размещаются в `src/modules/<название>`. Существующие модули CLI остаются в корне `src`.

Прикладные зависимости передаются через параметры конструктора с `@inject`; классы зарегистрированы в контейнере Inversify и помечены `@injectable`. Контейнер используется в точке входа, а компоненты зависят от интерфейсов.

### Файл `Readme.md`

Инструкции по работе с учебным репозиторием.

### Файл `Contributing.md`

Советы и инструкции по внесению изменений в учебный репозиторий.

### Остальное

Все остальные файлы в проекте являются служебными. Пожалуйста, не удаляйте и не изменяйте их самовольно. Только если того требует задание или наставник.

## Спецификация REST API

Контракт API описан в `specification/specification.yml` в формате OpenAPI 3.0.3. В нём определены предложения, комментарии, регистрация, вход, проверка пользователя, выход, премиальные предложения и избранное. Спецификация описывает планируемый HTTP API; серверные маршруты будут реализованы отдельно.

Аутентификация использует серверные сеансы: токен передаётся в `Authorization: Bearer <token>`, а выход отзывает сеанс. Публичные ресурсы допускают запросы без токена. Избранное определяется для текущего пользователя, для анонимного клиента `isFavorite` равен `false`.

Для просмотра откройте файл в PyCharm с совместимым OpenAPI-плагином либо в [Swagger Editor](https://editor.swagger.io/) через меню **File → Import file**. Расширения VS Code для работы в PyCharm не требуются.

Проверка спецификации отдельным линтером без изменения зависимостей проекта:

```bash
npm exec --yes --package=@redocly/cli@1.34.5 -- redocly lint specification/specification.yml
```

## Переменные окружения

Конфигурация загружается через dotenv из `.env` в текущей рабочей директории и проверяется convict. Переменные среды процесса имеют приоритет над `.env`. Все три параметра обязательны, рабочих значений по умолчанию нет. При отсутствии или невалидном значении запуск завершается с кодом 1. Значения соли и адреса базы в логи не попадают. CLI эти параметры не требует.

- `PORT=3000` — номер порта приложения (целое число от 0 до 65535).
- `DB_HOST=127.0.0.1` — валидный IPv4 или IPv6 адрес сервера MongoDB.
- `SALT=example-change-this-random-string` — непустая строка со случайными символами для хеширования паролей; замените пример собственным значением.

`.env` и локальные `.env.*` исключены из Git. `.env.example` содержит только демонстрационные значения.

### Читаемые логи

`npm run start:pretty` собирает и запускает приложение, направляя JSON-логи pino в pino-pretty. Код ошибки приложения сохраняется благодаря `pipefail`. pino-pretty установлен только как зависимость разработки.
